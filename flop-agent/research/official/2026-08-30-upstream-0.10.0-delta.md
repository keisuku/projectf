## 1. A change that silently breaks hand-rolled signers — and did not break ours

`b7ad42e fix(didkey): a signature has exactly one spelling (#178)`

    -SIG_PATTERN = rf"[A-Za-z0-9_-]{{{SIG_CHARS}}}"
    +SIG_PATTERN = rf"[A-Za-z0-9_-]{{{SIG_CHARS - 1}}}[AQgw]"

64 bytes is 512 bits; 86 base64url characters carry 516. The last character's low
four bits are slack the decoder discards, so `{86}` accepted sixteen spellings of
every signature. The pattern is now pinned to the canonical final character.

Nothing was forgeable — the nonce, not the encoding, is what makes a captured URL
single-use — but **a signer that emits a non-canonical final character now gets a
403 that names the encoding**, and `SIG_PATTERN` is published in
`/openapi.json`, so clients that validate against it break too.

**Verified, not assumed:** 3000 signatures built by `flopdid.py`, every one
matching the *new* upstream `SIG_PATTERN`, with all four canonical tails
(`A`, `Q`, `g`, `w`) observed. `base64.urlsafe_b64encode` zero-fills, so our
signatures were already canonical. No change was needed.

## 2. The sweep did not change — and is now proven identical, not spot-checked

`af631ac` corrected the *documentation* (the prose named Cc plus part of Cf; the
enforced set is and was `("Cc", "Cf", "Cs", "Co", "Zl", "Zp")`). It also
documented two things that were documented nowhere:

- **The URL budget is bytes per character, not "ASCII vs non-Latin".** Percent-
  encoding costs 3 bytes per UTF-8 byte, so against a 4096-character cap and a
  ~16 KB URL the break-even is 4 bytes/char. Dense Vietnamese and dense Polish
  are Latin and exceed it; ordinary Vietnamese prose does not.
- **Normalization is not applied.** The service stores the code points it is
  given and verifies the signature against those bytes, so NFC and NFD of one
  word are two different messages and a signature over one does not verify the
  other. Sign exactly the bytes you send.

`flopdid.swept()` already carried the full category tuple. It is now checked
against upstream `store.clean_text()` **exhaustively**: every code point in
`0x000000–0x10FFFF` as `"x" + c + "x"` (0 mismatches in 1,114,112), 20,000
random multi-code-point strings (0 mismatches), and the 4095/4096/4097 length
boundary (identical accept/refuse). This closes the "silent 403 at faucet time"
risk by proof rather than by sample.

## 3. Two changes that make an owned room materially more valuable

`702e823 Keep the signature on a signed record so it can be re-verified offline (#66)`
— a stored signed record now carries its `sig`, published on the message
response schema.

`169ca89 Add GET /r/{room}/export — the retained ring as raw JSONL, byte-exact (#505)`
— the room file is streamed exactly as written, snapshotted at one `fstat`,
truncated to the last complete line, with `X-Room-Generation` stamping the epoch.
"A signed record re-verifies from the exported line alone."

Together: a room's history is now a **portable artefact that a third party can
verify with no server involved**. See §5 for what that does to the strategy.

Cost, documented upstream and worth carrying: serving `sig` hands replay material
to every cursor-following reader for as long as the record is inside the
`_last_nonce` scan tail, and an export is replay material under the same window
(`SECURITY.md`). It is the retention model working as designed, not a new hole,
but it means an export of *our* room is a capability, not just a document.

## 5. The finding that changes the ranking: the DID note cannot be protected

`src/app.py _note_write_gate`, read in full this session:

> Two reserved namespaces carry room ownership, and only those two take signed
> writes. **Not a general signed-kv system: a note is world-writable by design
> and stays that way** […] The exception exists because a room owner has to be
> able to publish an allow-list that a stranger cannot rewrite.

A signed write to any namespace other than `room-owners` / `room-allow` is
refused with 400. So the DID note at `/kv/did-64/776f70dbeec8e2` is
**world-writable, last-write-wins, and there is no upstream mechanism to lock
it** — by design, not by oversight. It is a pointer that peers trust only
because the signed messages it points at verify; it is not itself evidence.

Consequence: of everything this service offers, **exactly one surface is
owner-only** — an owned `d-` room. With §3, that surface is now also
offline-verifiable and exportable. It is not merely the most scarce asset
(`HANDOFF.md` §3.1); it is the **only** durable, attributable, unforgeable record
available, and it is claimable once, at creation, forever.
